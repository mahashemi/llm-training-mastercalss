# Contributing

Thank you for helping improve the LLM Trainer Masterclass.

This repository is an open educational and research resource. Contributions are welcome from students, educators, engineers, researchers, and organizations.

## What makes a strong contribution?

Strong contributions are technically correct or explicitly exploratory, reproducible, clearly scoped, grounded in strong sources, tested on the stated environment, and explicit about assumptions and limitations.

Useful contributions include new explanations, figures, notebooks, experiments, failure analyses, paper guides, translations, benchmark tasks, resource-planning tools, and case studies.

## Before contributing

Search existing issues and pull requests first.

For substantive changes, open an issue or discussion describing the problem, proposed improvement, beneficiaries, evidence or references, and expected maintenance burden.

## Notebook requirements

A practical notebook should:

- run from a clean Colab or documented environment where feasible;
- verify or install dependencies explicitly;
- state expected hardware and approximate resource requirements;
- demonstrate a small controlled case before scaling;
- show intermediate observations;
- include sanity checks;
- report failures and limitations;
- never contain secrets, credentials, or private data.

## Research experiment requirements

Research-oriented experiments should record the hypothesis, baseline, independent variables, dataset/version, model/version, tokenizer, training configuration, hardware, software versions, evaluation protocol, metrics, result, uncertainty where meaningful, failure analysis, and limitations.

## Source discipline

For major technical claims, prefer:

1. primary research papers or official technical reports;
2. official documentation;
3. original course material from the authors;
4. reputable secondary technical explanations.

Do not silently turn a heuristic into a universal law. Label rules of thumb, estimates, assumptions, and empirical observations.

## Pull requests

A useful pull request should explain what changed and why, identify affected material, include tests or reproduction notes where applicable, update references when claims change, and update the changelog for substantial user-visible changes.

## Teaching quality

New material should separate intuition, formalism, implementation, and engineering judgment. When a concept is difficult, use examples, diagrams, tensor shapes, controlled experiments, and counterexamples instead of unexplained jargon.

## AI-assisted contributions

AI tools may be used as development aids, but contributors remain responsible for factual accuracy, provenance, licensing, code correctness, experiment validity, citations, security, and privacy.

## Review standard

Reviewers should ask:

- Is it correct?
- Can another person reproduce it?
- Is the explanation understandable?
- Does it improve engineering judgment?
- Could it mislead a future learner or practitioner?

A contribution is valuable when it makes the repository more useful without making it less trustworthy.
